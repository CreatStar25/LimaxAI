## 3 万亿级参数和 100 万 Token，先把规格看清楚

K3.1 Pro 是 K3.1 系列推出的首个模型。官方把它称为迄今能力最强的 3 万亿级参数模型，同时推出 Highspeed 高速版。这里的 3 万亿级描述的是模型参数规模，不能自行理解成每次推理都会激活同样数量的参数，官方这份指南没有给出可据此计算的激活参数表。

先看能核实的规格，少一点猜测。

| 项目 | 官方文档公布的信息 |
|---|---|
| 标准版模型 ID | `kimi-k3.1-pro` |
| 高速版模型 ID | `kimi-k3.1-pro-highspeed` |
| 参数规模 | 3 万亿级 |
| 上下文窗口 | 1,048,576 Token，通常简称 1M |
| 思考模式 | 始终开启 |
| 推理强度 | `low`、`high`、`max`，默认 `max` |
| `max_completion_tokens` | 默认 131,072，最大可设置为 1,048,576 |
| 视觉能力 | 官方 API 支持图片和视频理解 |
| 高速版速度 | 官方称相同智能水平下，输出速度约为标准版的 2 至 3 倍 |
| 权重发布 | 官方计划在 2026 年 11 月 4 日前发布完整模型权重 |

规格依据为[模型指南](https://platform.kimi.com/docs/guide/kimi-k3-1-pro-quickstart)、[模型列表](https://platform.kimi.com/docs/models)和[视觉输入文档](https://platform.kimi.com/docs/guide/use-kimi-vision-model)。输出参数的最大设置值，不等于任何输入长度、任何服务渠道下都能生成同等长度的回答。

还有一个时间上的区别。今天可以通过服务调用模型，和完整权重已经能下载，是两回事。官方写的是 11 月 4 日前的发布计划，所以这篇文章不会把它提前写成已经开放权重，更不会替它补上尚未确认的许可证。

说真的，参数大只是起点。写一段代码能不能跑，改完一个模块会不会弄坏另一个模块，做研究能不能把出处留下来，这些事才会决定它有没有帮上忙。

## 天宫、机场和涡扇结构，三个官方案例值得拆开看

回到开头那座天宫。它有长廊、云层、建筑和角色活动，镜头移动时，场景的空间关系仍然成立。官方将这段视频列在编码案例中，并说明展示案例由 K3.1 Pro 端到端完成。

这里要看的，不只是画面漂亮。一个可运行场景还要处理对象、位置、材质、光照和交互之间的关系。对做网页、游戏或产品原型的人来说，更有用的起点往往是一份可修改的场景结构，而不是一张只能参考的效果图。

但我没有拿到这个案例的完整工程，也没有在 LimaxAI 里重跑它。仅凭展示视频，我们无法确认所有代码质量、制作耗时或后续维护成本。把它当作能力展示很合适，直接当成交付保证就走远了。

第二个例子换到机场室内场景。玻璃穹顶、环形步道、植物和中央水景都在画面里，官方文件将它标为 Blender 案例。

## 100 万上下文适合长材料，聊天页仍有自己的边界

很多人看到 1M，第一反应就是整份资料直接塞进去。

长上下文确实能减少来回搬运材料的次数。可输入放得下，与模型能找准每一个关键信息，中间还有检索、理解和核验这些步骤。材料越多，越值得给它一份清楚的任务范围，告诉它哪些结论必须能回到原文核对。

还要分清模型与产品。官方 API 的参数上限、Kimi 自家应用的功能，以及 LimaxAI 聊天页开放的功能，并不是同一张清单。

| 能力 | Kimi 官方模型或 API | LimaxAI 当前体验入口 |
|---|---|---|
| 文字对话与流式回答 | 支持 | 可体验 |
| 1M 上下文窗口 | 官方模型规格 | 按聊天页输入及文件限制使用，不承诺开放完整 1M |
| 图片和视频理解 | 官方 API 支持 | 当前 Kimi 入口未开放这些上传能力 |
| 推理强度选择 | `low`、`high`、`max` | 当前聊天页不提供对应档位开关 |
| 自定义工具调用 | 需要接入工具并执行调用循环 | 普通聊天入口不等于自动运行本地建模软件 |
| 3D 工程交付 | 官方展示了带软件环境的案例 | 可讨论方案与脚本，执行和验收仍需实际软件环境 |

官方的[视觉输入文档](https://platform.kimi.com/docs/guide/use-kimi-vision-model)说明了图片与视频请求格式，工具调用流程则见[模型指南](https://platform.kimi.com/docs/guide/kimi-k3-1-pro-quickstart)。上表将这些模型能力与本站当前入口分开列出，避免看完演示视频，以为打开聊天框就已经装好了 Blender。

其实吧，这样分清楚之后，使用起来反而更直接。先让 Kimi 帮你拆需求、读代码、写脚本或整理资料；需要执行的时候，再把产物放到对应环境里测试。把任务分到能验证的一步，比追求一次把所有事做完更可靠。

## 程序员、3D 创作者和研究人员，可以从小任务开始

程序员可以从边界清楚的改动开始。给出相关函数、报错、预期行为和不能改的接口，让 Kimi 先解释问题，再提出最小改动。这样你能区分它是在读代码，还是仅凭报错关键词套用常见答案。

下面是一段可复制的起手任务，不是我们已经跑出的测试结果。

```text
我会贴出一个函数、调用方式和实际报错。
请先说明你能从这些信息确认什么，还有什么不能确认。
保持函数签名和返回结构不变，提出最小改动方案。
如果需要其他文件，先明确指出，不要自行编造项目结构。
给出能够验证修复是否有效的测试步骤。
```

3D 创作者可以先让它写可调参数的建模脚本。对象数量先少一点，尺寸、材质和相机位置留成参数。确认最小场景能运行，再增加复杂度，远比一上来要求重做整座机场容易排查。

```text
请为 Blender 设计一个可通过 Python 脚本生成的展示场景。
先列出需要的对象、命名方式和可调参数，再给出脚本。
不要假设我已经安装第三方插件。
请说明适用的 Blender 版本，并把执行方式和验收步骤写清楚。
遇到无法确认的接口，不要用猜测的函数名代替。
```

做研究的人，可以把第一轮任务设成证据整理，而不是写一个漂亮结论。对于几份材料之间有冲突的地方，要求它并列保留，别急着消掉分歧。模型愿意承认缺了什么，往往比回答长不长更有参考价值。

```text
请只根据我提供的材料整理一张证据表。
逐项列出指标、数值、期间、单位和原文位置。
把事实、材料中的观点和你的推断分开。
缺少信息就标记未找到，出现冲突就同时保留并说明差异。
暂时不要给投资结论，也不要补充没有出处的数字。
```

这几个起点都不复杂。把同一段任务交给 Kimi，再用自己已经熟悉的模型做一次，对比有多少结果能直接检查、多少内容还得返工。如果你还在挑选其他模型，可以接着看站内的 [Gemini 4 Argon 评测对比](https://blog.limaxai.com/zh-cn/gemini-4-argon-benchmarks-vs-gpt6-claude/)，把不同任务的优势放在一起判断。
